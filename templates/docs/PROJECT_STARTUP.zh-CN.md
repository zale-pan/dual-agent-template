# 轻量 P0：新项目启动核对

Steward 在首个业务任务下发前完成本清单。手工使用时在轮次工作单首栏记录当前结论；结构化项目在 DEVELOPMENT_STATUS.json 的 project_startup 中维护，工作单只引用它。初始状态 pending；复制模板、用户同意项目目标、模板自身测试通过，均不能把状态改为 ready。

## 启动时核对什么

| 项目 | 达到什么条件 |
|---|---|
| 项目与身份 | 用户确认项目根、首个任务的目标和成功条件，指定 Steward、实施 Agent 和批准人。Steward 能定位真实源码、测试入口和原有改动。 |
| 权限与交付 | 工作单列出可写路径和操作、保护对象、外部输出位置。说明谁批准、从哪里读回冻结输入、由谁独立验收并关闭权限。 |
| 验收能力 | 写出工作目录、命令、环境以及观察哪个结果。逐项标明由 Steward 人工检查，还是依赖某个自动检查；明确需要事后发现还是写入前阻止。 |
| 存储与收尾 | 指定暂存根、消费者和释放条件；每轮最终一份简短总结。清理沿用逐项批准和读回规则。 |

## 首轮依赖的每个自动检查都要实测

在目标项目的实际工具入口，以首轮相同的工具版本、配置、路径语义和执行身份运行。用可丢弃的合成夹具，记录检查名、入口或命令、适用环境、正反例的输入、预期、实测及结论。已有该项目相同条件下的实测可按指纹复用。尚未使用的工具不用演练。

例如，首轮依赖范围检查器时，正例只改变已批准的样例文件，应允许；反例额外改变一个未批准的样例文件，应拒绝并指出该路径。如果承诺写入前拦截，反例还须通过实际受限写入入口并核对目标原始字节未变。只看到事后差异不能证明预防生效。工具未运行、夹具未抵达检查入口、合法输入被拒、反例被放过或副作用不符，都记下实际结果并保留阻断原因。

## 启动裁决与下发

| 核对结果 | Steward 行动 |
|---|---|
| 所需检查均可由人工可靠完成，合同也允许人工检查 | 写明每项检查由谁、在何时、如何判定。自动检查清单可为空；其余启动项齐备后记 ready。 |
| 首轮依赖自动检查，所有相关正反例均达到预期 | 在当前状态记录适用边界与实测结论；其余启动项齐备后记 ready。 |
| 必需自动检查缺失、与项目不兼容或对照失败 | 记 blocked，列出受阻业务能力。先排除命令、夹具或环境问题，仅复测受影响项。若需开发、修改或接入工具，单独拟治理适配合同，写明精确范围和通过条件；用户批准并下发后仅开放适配范围。Steward 在目标环境独立复验通过，再重新裁定启动状态。 |
| 要改用人工替代自动检查 | 仅当可满足同一实际要求，或用户明确批准变更该要求时，修订合同，重新核对并记录。不能用事后人工审阅冒充事前强制拦截。 |

**业务放行有两个条件。** 项目启动结论为 ready，且该业务轮次已有用户批准。Steward 才能冻结下发；实际交付位置读回一致后，实施者才获得该轮精确写权限。pending、blocked 或缺少结论时，业务权限关闭。适配任务使用自己单独批准的授权；其通过不会自动批准业务轮次。

工具、权限、配置、工作区或执行身份发生影响结论的变化时，将受影响能力标为待复核，在后续任务依赖它之前补测。当前状态只留有效结论、依据和未解项；临时输出按消费者释放，适配轮沿用一份短总结。
