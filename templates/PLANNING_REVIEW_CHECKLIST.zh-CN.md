# 项目拆解与任务清单审查

## 1. 需求基线

- [ ] 项目用户、问题、期望结果和初始交付物明确。
- [ ] 已区分事实、假设和未知项。
- [ ] 会导致不同架构的未知项已关闭或交由用户决定。
- [ ] 输入、输出、数据敏感性和版本可用性已记录。
- [ ] 非目标、时间/成本限制和受保护面已确认。

## 2. 目标与验收条件

- [ ] 每个 Goal 有稳定 ID、可观察结果和至少一个 AC。
- [ ] AC 描述行为/指标，而不是“文件存在”或“接口已定义”。
- [ ] 尚无数据支持的数值阈值标为 TBD，没有编造指标。
- [ ] 每个 Goal 记录计划组件、验证协议和已知限制。
- [ ] 非目标没有被任务清单偷偷重新引入。

## 3. 架构和组件边界

- [ ] 每个组件有单一责任、owner、输入、输出和依赖。
- [ ] 组件 registry 声明 availability、path scope、mutation mode、验证和回滚。
- [ ] 原始数据、评测器、凭据、权限、生产端点和参考代码已标 protected。
- [ ] 禁止耦合和数据所有权明确。
- [ ] 尚未确认的供应商私有格式没有被固化。

## 4. 阶段拆解

- [ ] 阶段按依赖和可验证成果划分，而非按团队/目录。
- [ ] 每阶段有前置条件、核心结果、完整任务列表和 exit gate。
- [ ] readiness 和 blocker 有事实依据、owner 和解除条件。
- [ ] 后续阶段没有被提前塞进当前阶段。
- [ ] 离线可推进内容不会因真实服务未接入而无故阻塞。

## 5. 全量任务清单

- [ ] 每个任务只有一个主要结果并可独立验收。
- [ ] 每个任务都有 goal_refs、acceptance_refs 和 dependencies。
- [ ] 每个任务都有 in/out scope、错误模型、测试矩阵和验证方法。
- [ ] 没有孤立任务、重复任务、循环依赖或无法判断成功的任务。
- [ ] 实现顺序符合依赖；第一项 next action 的所有前置均已满足。
- [ ] 调查/spike 任务有明确输出，不能无限期代替实现。

## 6. 追踪完整性

- [ ] 每个 AC 至少映射一个任务或明确 deferred/non-goal。
- [ ] 每个任务映射的 Goal/AC 都真实存在。
- [ ] Phase exit gate 可由该阶段任务证据共同支持。
- [ ] Traceability Matrix 没有 orphan goal/AC/task。
- [ ] 当前成熟度没有超过 evidence 支持的等级。

## 7. 进入双代理执行层

- [ ] 全量清单已完成，但只选择第一项依赖已满足的任务进入商讨。
- [ ] 已创建中文 consultation，展示方案、范围、文件、错误模型、测试和取舍。
- [ ] 重大待决问题已由用户明确决定并写入 consultation。
- [ ] 用户已明确同意进入编码，consultation_status=`agreed`。
- [ ] 未经商讨确认的任务仍是 draft，未生成可执行 instruction。
- [ ] 当前任务 manifest 只授权精确文件。
- [ ] CURRENT_TASK、next action、task doc 和 manifest 一致。
- [ ] project/scope check 正负演练通过。
- [ ] 用户已能通过中文视图理解目标、路线、任务、风险和当前进度。
